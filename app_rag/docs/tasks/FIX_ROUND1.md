# 1차 문제 해결 (FIX_ROUND1)

`CLAUDE.md`의 절대 규칙을 그대로 따른다. 아래 A→B→C→D를 **순서대로** 하고, 단계마다 `docs\PROGRESS.md`에 "FIX_ROUND1-A" 같은 제목으로 기록한다. D까지 끝나면 **멈춘다.** MVP_PLAN 3단계(임대·차용 카드)는 2차에서 한다.

정답지 자체(라벨·근거 문구)는 이번에 고치지 않는다. 정답 근거가 애매해 보이는 건은 목록으로만 남긴다.

## 지금 문제 (사용자와 합의한 것)
1. dev에 깨끗한 계약서가 너무 적다. 임대·근로는 1장, 차용은 2장.
2. dev가 작다(근로 독소 19개). 그런데 같은 dev로 다섯 번 고쳤다.
3. 모델 비교가 불공정하다. 프롬프트·검증 규칙을 A.X에 맞춰 고친 상태로 EXAONE을 돌렸다. 특히 `ax_review_to_ok`가 EXAONE의 독소 경고 8개를 지웠다.
4. 지표가 "위반·위험"만 탐지로 센다. 신중하게 "확인 필요"로 답하는 모델이 불리하다.
5. A.X 임대 탐지가 DEV_EVAL 0.115에서 AX_VS_EXAONE 0.808로 올랐는데 원인을 모른다.
   - 의심 1: 지금 `prompts\judge.txt`의 "criteria의 violation 목록이 비어 있으면 위반·위험으로 답하지 않는다" 줄이 카드가 없는 임대·차용에서 어떻게 들어가는지 모른다.

## A. 데이터: dev 늘리기 + 깨끗한 계약서 세트 (문제 1·2)
datasets 원본 파일은 고치지 않는다. 새 파일만 만든다.

### A-1. dev를 약 30%로 늘리기
- `datasets\splits\dev_test_split.json`은 그대로 두고, 새 파일 `dev_test_split_v2.json`을 만든다.
- **지금 dev 문서는 전부 dev에 남긴다.** 이미 튜닝에 쓴 문서라 test로 옮기면 안 된다.
- 모자란 만큼만 test에서 dev로 옮긴다. 독소 개수 구간(0 / 1~2 / 3~5 / 6+)별 비율을 유지하고 seed 42.
- 목표: 임대 15/35, 차용 18/42, 근로 12/28 (dev/test 문서 수)
- test 문서는 지금까지 한 번도 돌리지 않았으므로 옮겨도 된다. 옮긴 문서 ID를 기록한다.

### A-2. 깨끗한 계약서 세트 ("clean twin")
- 도메인마다 dev 5장, test 5장을 만든다.
- **만드는 법:**
  - 같은 분할 안의 독소 있는 문서를 하나 고른다.
  - 그 문서의 toxic·check 조각을 **같은 분할 안 다른 문서**의 같은 `std_item` safe 조각으로 바꾼다.
  - dev 문서는 dev에서만, test 문서는 test에서만 가져온다. 섞으면 dev 튜닝이 test에 새어 들어간다.
- 같은 std_item의 safe 조각이 없으면 그 조각은 빼고, 뺀 수를 기록한다.
- **근로 일관성 검사:**
  - 바꾼 뒤 `rag/facts.py`와 숫자 규칙(최저임금 연도표, 휴게)을 돌린다.
  - 규칙이 하나라도 걸리면 그 문서는 버리고 다른 문서로 다시 만든다.
  - 시급이 계약기간에 해당하는 연도 최저임금 이상인지 꼭 본다.
- 저장: `datasets\<도메인 폴더>\clean_twins\01_계약서.jsonl`
  - doc_id는 `LEASE-C001`, `LOAN-C001`, `WORK-C001` 형식
  - 모든 조각의 label은 safe 또는 meta, toxic_code는 `[]`
  - 어느 문서에서 만들었는지(`twin_of`)와 분할(`split`)을 필드로 남긴다
- `dev_test_split_v2.json`에 clean twin 문서도 dev/test로 넣는다.

### A-3. 확인
- 도메인별 표: dev/test 문서 수, 독소 있는 문서 / 깨끗한 문서 수, 독소·확인 필요·안전 조각 수
- clean twin에서 숫자 규칙으로 버린 문서 수와 이유

## B. 지표 보강 (문제 4)
평가 코드(`dev_eval.py`, `lab_cards_connect_eval.py`, `ax_vs_exaone_eval.py`)가 같은 채점 함수를 쓰게 정리하고, 아래 지표를 추가한다. 기존 지표는 그대로 둔다.
- **경고 포착률:** toxic 중 위반·위험·확인 필요를 받은 비율. 기존 "탐지율(위반·위험)"과 나란히 낸다.
- **문서 판정:** 문서마다 리포트 맨 위 3단계 문구를 계산한다.
  - 위반·위험 0, 확인 필요 0~2 → "큰 문제 없음"
  - 위반·위험 0, 확인 필요 3 이상 → "확인할 부분 있음"
  - 위반·위험 1 이상 → "고칠 조항 있음"
- **깨끗한 문서 통과율:** 깨끗한 문서(원래 깨끗한 문서 + clean twin) 중 "큰 문제 없음"이 나온 비율
- **독소 문서 경고율:** 독소 있는 문서 중 "고칠 조항 있음"이 나온 비율
- **95% 신뢰구간(Wilson):** 모든 비율 옆에 붙인다. 표본이 작아 숫자가 흔들리는 정도를 보이기 위해서다.
- `ax_review_to_ok`가 독소를 덮어쓴 수와 안전을 덮어쓴 수를 따로 센다.

## C. 임대 점수 급등 원인 찾기 (문제 5)
1. DEV_EVAL 때와 지금 사이에 바뀐 것을 표로 낸다. 열: 파일, 바뀐 줄, 임대에도 적용되는지.
   - 대상: `judge.txt`, `verify.py`, `retrieve.py`, corpus, `pipeline.py`
2. 카드가 없는 도메인(임대·차용)에서 `<criteria>` 블록에 실제로 무엇이 들어가는지, 프롬프트 원문 1건을 붙인다(계약서 문장은 `…`로 가린다).
3. 의심 줄("criteria의 violation 목록이 비어 있으면…")이 카드 없는 도메인에서 위반을 막고 있는지 확인한다.
   - 막는 게 맞으면, 그 줄은 **카드가 있을 때만** 넣도록 고친다. 기록을 남긴다.
4. 지금 임대 dev(옛 dev 10장)로 두 번 돌려 원인을 가린다. 각 8분 안팎.
   - 옛 judge(`judge_v1.txt`) + 지금 나머지
   - 지금 judge + 지금 나머지
   - 탐지율·경고 포착률·오탐률을 비교한다. 3번에서 고쳤으면 고친 버전도 한 번 더 돌린다.

## D. 공정 비교와 새 기준점 (문제 3)
1. `ax_review_to_ok`를 설정값(`config`)으로 바꾼다. 켜기/끄기가 가능해야 한다. 기본값은 지금처럼 켜기.
2. **새 dev(A-1, clean twin 포함)로 아래 4가지를 돌린다. 근로만, 카드는 그대로.**
   | 실행 | 모델 | ax_review_to_ok |
   |---|---|---|
   | D1 | A.X | 켜기 |
   | D2 | A.X | 끄기 |
   | D3 | EXAONE | 켜기 |
   | D4 | EXAONE | 끄기 |
   - EXAONE은 지난번처럼 A.X를 잠시 내리고 8083에서 단독으로 돌린다. 끝나면 A.X 8082를 다시 띄운다.
   - 돌리기 전에 예상 시간을 적는다. 합계가 90분을 넘으면 묻는다.
3. **새 기준점:** 같은 새 dev로 임대·차용을 A.X 기본 설정(C에서 고친 것 반영)으로 한 번 돌린다. 이게 2차 작업의 출발점이 된다.
4. 결과는 B의 지표 전부로, 도메인별 표로 낸다. 신뢰구간을 포함한다.
5. **판정 모델은 정하지 않는다.** 아래 기준에 비춰 어느 쪽이 나은지만 적는다.
   - 경고 포착률 90% 이상
   - 오탐률 5% 이하
   - 깨끗한 문서 통과율 80% 이상
   - 조항당 시간
