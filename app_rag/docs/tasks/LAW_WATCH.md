# 법령 개정 추적 → 카드 버전 관리 (LAW_WATCH) — 개정판

**이 문서가 이전 LAW_WATCH.md를 대체한다.** 이미 만든 것이 있으면 버리지 말고 이 문서에 맞춰 이어서 고친다.

**목표:** 법령이 바뀌면 감지 → 조문 비교 → 영향받는 카드 찾기 → EXAONE이 카드 수정안과 적용 기준 초안 작성 → 관리자 승인 → 새 **카드 버전**으로 등록 → 빠른 점검 → 필요하면 되돌리기. 분석할 때는 **계약서 날짜에 맞는 카드 버전**을 골라 쓴다.

## 결정 사항
1. **카드는 항목당 하나다. 날짜별로 카드를 따로 만들지 않는다.** 대신 카드마다 **버전**을 쌓는다.
2. 버전마다 **시행일**과 **적용 기준**을 가진다. 적용 기준은 개정법 **부칙**에서 정해진다. 셋 중 하나다.
   | 적용 기준 | 뜻 | 고르는 방법 |
   |---|---|---|
   | `contract_date` | 시행일 이후 새로 맺거나 갱신한 계약부터 적용 | 계약일(갱신이면 갱신일)에 시행 중이던 버전 |
   | `in_force` | 시행일에 진행 중인 계약에도 적용 | 오늘 시행 중인 버전 |
   | `performance_period` | 이행 시점마다 그때 기준을 적용 | 계약기간에 걸친 기간마다 해당 버전을 각각 적용 |
3. 적용 기준을 알 수 없으면(`unknown`) 추측하지 않는다. 계약일이 그 버전 시행일보다 앞인 조항은 "확인 필요"로 보내고 "개정 전후 기준이 다를 수 있어요"라고 안내한다.
4. 카드와 적용 기준은 **관리자가 승인해야만** 바뀐다. 모든 변경은 버전으로 남기고 되돌릴 수 있다.
5. **버전이 하나뿐인 카드는 지금과 완전히 똑같이 동작해야 한다**(평가한 시스템과 같아야 한다).

`CLAUDE.md` 규칙을 따른다.
- 고칠 파일은 `*_v숫자`로 백업한다(삭제 금지).
- 키 값은 출력하지 않는다.
- test 평가는 다시 돌리지 않는다.
- 검색·모델 설정은 바꾸지 않는다.
- 숫자마다 명령과 출력 파일 경로를 붙인다.

## 다른 작업과 부딪히지 않게
다른 채팅에서 **FINAL_POLISH**가 `server.py`, `static\`, 기존 `rag\*.py`를 고치고 있다.
- **1단계(지금):** 1~6장과 9장을 **새 파일로만** 만든다. 폴더는 `rag\lawwatch\`, `eval\lawwatch_*.py`, `data_local\law_versions\`, `criteria\versions\`, `criteria\proposals\`, `tests\test_lawwatch.py`다. 기존 파일은 읽기만 한다.
- **2단계(`out\polish\POLISH_REPORT.md`가 생긴 뒤):** 7~8장(판정 파이프라인 연결, 화면)을 한다. 10분마다 확인하며 기다린다. 4시간이 지나도 안 생기면 1단계 결과만 보고하고 멈춘다.

## 1. 법령 버전 저장소
- `data_local\law_versions\{법령명}\{식별자}.json`에 본문(조문과 **부칙**)을, `index.json`에 법령명·MST·공포번호·공포일·시행일·가져온 시각·상태(현행/예정/과거)를 둔다.
- 기준선: 지금 corpus를 만든 `..\data_contract\law_api\현행\*_body_MST.json`을 "현행"으로 등록한다. `..\data_contract\law_api\연혁*`의 과거 버전도 "과거"로 등록한다.
- 대상: `corpus\records.json`과 카드 3벌의 basis에 나오는 법령 전부, 그리고 숫자 고시(최저임금 고시, 최고이자율 규정).

## 2. 감지 (`rag\lawwatch\check.py`)
- 국가법령정보 공개 API로 대상 법령의 최신 MST·공포번호·시행일을 조회해 index와 비교한다. 호출 방식은 `data_contract`를 만든 스크립트를 따른다.
- 결과 상태: `변경 없음` / `개정됨(시행 중)` / `개정 예정(시행일이 미래)`
- API 키가 없거나 호출이 실패하면 멈추지 않고 **오프라인 모드**(저장소에 있는 두 버전끼리 비교)로 돌고, 그 사실을 결과에 적는다.
- 실행 방법: `python -m rag.lawwatch.check`. 서버 시작 시와 24시간마다 실행하는 것과 관리자 화면의 "지금 확인" 버튼은 2단계에서 연결한다.

## 3. 조문 비교와 영향 찾기 (`rag\lawwatch\diff.py`)
- 조·항 단위로 `추가 / 삭제 / 변경`을 내고 전·후 문장을 함께 낸다. 띄어쓰기·기호만 다른 것은 "형식 변경"으로 분류한다.
- ID는 corpus와 같은 형식(`law:근로기준법:17`)으로 맞춘다.
- 영향:
  - 카드 basis에 그 ID가 있는 카드 → 영향받는 카드
  - `records.json`에서 그 ID인 조각 → 다시 색인할 조각
  - 숫자 기준(최저임금, 최고이자율, 증액 한도 등)의 변화는 따로 표시
- **부칙 추출:** 그 개정의 부칙에서 "시행일", "적용례", "경과조치" 문장을 뽑아 같이 저장한다.
- 출력: `out\lawwatch\{날짜}_changes.json`, `_changes.md`

## 4. 카드 버전 파일 (`criteria\versions\{카드ID}.yaml`)
```yaml
card_id: LOAN-INTEREST
versions:
  - version: 1
    effective_from: "2018-02-08"     # 이 기준의 시행일
    effective_to: "2021-07-06"
    apply_rule: contract_date        # contract_date | in_force | performance_period | unknown
    rule_source:                     # 적용 기준의 근거(부칙 원문 그대로)
      law: "이자제한법 제2조제1항의 최고이자율에 관한 규정"
      quote: "(부칙 문장을 원문 그대로)"
    card: { safe: [...], violation: [...], check_if: [...], basis: [...] }
  - version: 2
    effective_from: "2021-07-07"
    effective_to: null
    apply_rule: contract_date
    rule_source: {...}
    card: {...}                      # 지금 criteria\*_cards.yaml 의 그 카드와 같은 내용
```
- 지금 카드 파일(`criteria\*_cards.yaml`)은 그대로 "현행 버전"이다. 버전 파일이 없는 카드는 현행 하나만 있는 것으로 본다.
- `rule_source.quote`는 저장소의 부칙 원문에 **실제로 있는 문장**이어야 한다(코드로 포함 여부를 검사한다). 못 찾으면 `apply_rule: unknown`으로 둔다.

## 5. 버전 고르기 (`rag\lawwatch\select.py`)
`select_versions(card_id, contract_date, period_start, period_end, today)`가 적용할 버전 목록과 안내 문구를 돌려준다. 계약일·계약기간은 `rag\dates.py`가 뽑은 값을 쓴다.

| 상황 | 결과 |
|---|---|
| 버전이 하나뿐 | 그 버전. 지금과 동작이 같다 |
| `contract_date` | 계약일(없으면 오늘)에 시행 중이던 버전 |
| `in_force` | 오늘 시행 중인 버전 |
| `performance_period` | 계약기간과 겹치는 버전을 모두 돌려준다. 숫자 기준은 기간마다 그때 값을 적용한다(최저임금 연도표 방식과 같다) |
| `unknown`이고 계약일이 시행일보다 앞 | 현행 버전 + "확인 필요" + 안내 "개정 전후 기준이 다를 수 있어요" |
| 계약기간 안에 시행 예정인 버전이 있음 | 지금 버전으로 판정 + 참고 안내 "계약기간 중 YYYY-MM-DD부터 기준이 바뀌어요: (바뀌는 내용 한 줄)" |
| 계약일을 못 뽑음 | 오늘 기준 버전 + 리포트에 "계약일을 찾지 못해 오늘 기준으로 봤어요" |

- 과거 버전으로 판정할 때 근거 조문은 법령 버전 저장소의 **그 시점 조문**을 쓰고, "시행 YYYY-MM-DD 기준"이라고 표시한다.

## 6. 수정안 만들기와 승인 (`rag\lawwatch\propose.py`, `apply.py`)
- **검색용 법령 모음:** 바뀐 조각만 새 문장으로 바꾸고 그 조각만 다시 임베딩해서 **새 버전 파일**로 만든다. 지금 파일은 둔다. BM25·bge-m3·RRF 설정은 그대로다.
- **카드 수정안:** 영향받는 카드마다 EXAONE(8083)에 `카드 원문 + 조문 전/후 + 부칙 문장`을 주고 JSON으로 받는다.
  - 형식: `{"needs_change": bool, "reason": "...", "proposed": {safe, violation, check_if, basis}, "apply_rule": "...", "rule_quote": "부칙 문장"}`
  - 제약: 바뀐 조문과 관련된 부분만 고친다. 카드 1장은 500자 이내. 정답 데이터 문장은 쓰지 않는다. 조문에 없는 내용과 숫자는 넣지 않는다.
  - 코드 검사: YAML 형식, 길이, basis ID가 새 법령 모음에 존재, 수정안의 숫자가 조문 전/후에 존재, `rule_quote`가 부칙 원문에 존재. 실패하면 "수동 수정 필요"로 표시하고 `apply_rule`은 `unknown`으로 둔다.
  - GPU를 다른 분석이 쓰고 있으면 기다린다.
- **숫자 표 수정안:** 최저임금·최고이자율이 바뀌면 `config\` 표에 값과 시행일을 추가하는 수정안을 만든다.
- 저장: `criteria\proposals\{날짜}_{카드ID}.yaml`(수정안, 전/후 비교, 이유, 적용 기준 초안, 상태 `대기`)
- `승인`:
  - 새 버전을 `criteria\versions\{카드ID}.yaml`에 추가한다(이전 버전의 `effective_to`를 채운다).
  - 시행일이 오늘 이전이면 현행 카드 파일과 법령 모음도 새 버전으로 바꾼다(바꾸기 전 `_v{n}` 백업).
  - 시행일이 미래면 `예약` 상태로 두고, 시행일 이후 첫 확인 때 현행으로 바꾼다.
  - `data_local\law_versions\applied_log.json`에 누가·언제·무엇을·평가 당시 카드 해시를 남긴다.
- `반려`: 수정안 상태만 바꾼다.
- `되돌리기`: 직전 상태의 카드·버전 파일·법령 모음으로 복구한다(파일 해시가 원래와 같아야 한다).
- **빠른 점검(승인 직후, test 금지):** dev 조각 중 영향받는 카드가 선택되는 조각만(최대 200개, seed 42) EXAONE으로 다시 판정해 적용 전/후의 경고 포착·오탐·과잉 경고를 `out\lawwatch\{날짜}_regression.md`에 적는다. 나빠지면 "주의"로 표시한다. 자동으로 되돌리지는 않는다.

## 7. 판정 파이프라인 연결 (2단계)
- 카드를 고르는 곳(`rag\criteria.py`)에서 `select_versions`를 불러 날짜에 맞는 카드 버전을 쓴다. 안내 문구는 리포트의 "직접 확인할 것"이나 참고에 넣는다.
- **같음 검사(필수):** 버전 파일이 없는 상태에서 dev 799조각의 판정 프롬프트 해시가 연결 전과 **799/799 같아야** 한다. 다르면 연결을 되돌리고 보고한다.
- 리뷰를 저장할 때 법령 기준일과 사용한 카드 버전을 함께 저장한다.

## 8. 화면 (2단계)
- 관리자 화면에 **"법령 변경"** 탭(관리자만, 일반 사용자는 403):
  - 마지막 확인 시각, "지금 확인" 버튼
  - 변경 목록(법령 / 조 / 종류 / 시행일 / 전·후 / 부칙 문장)
  - 영향받는 카드, 수정안 전·후, 이유, 적용 기준 초안과 근거 문장
  - `승인` / `반려` / `되돌리기`, 빠른 점검 결과
  - 카드별 버전 이력(버전 / 시행일 / 적용 기준)
- 검토 리포트 화면:
  - "법령 기준일: YYYY-MM-DD"
  - 과거 버전으로 본 조항에는 "계약일 기준(시행 YYYY-MM-DD) 적용" 표시
  - 계약기간 중 예정된 개정이 있으면 참고 안내
  - 예전 기록을 열면 "분석 당시 기준일"
- 서버 시작 시와 24시간마다 `check`를 실행한다. 실패해도 서버는 계속 돈다.

## 9. 실제 사례 3개를 버전으로 등록 (1단계에서 준비, 시연용)
아래 세 사례를 4장 형식의 버전 파일로 만든다.
- **시행일과 부칙 문장은 저장소의 법령·연혁 파일이나 API에서 직접 찾아 원문 그대로 넣는다.** 기억이나 추측으로 쓰지 않는다. 못 찾은 항목은 "미확인"으로 적고 `unknown`으로 둔다.

| 사례 | 적용 기준(확인 대상) | 시연 장면 |
|---|---|---|
| 최저임금 2026년 10,320원 → 2027년 10,700원 | `performance_period` | 2026~2027년에 걸친 근로계약: 2027년 구간에 새 최저임금 적용 안내 |
| 최고이자율 연 24% → 20% (2021-07-07 시행) | `contract_date` (부칙으로 확인) | 같은 차용증 문장 "연 22%": 계약일 2021-06-01이면 당시 기준 이내 + 안내, 계약일 2026년이면 위반 |
| 주택임대차보호법 2020-07-31 개정 (계약갱신요구권, 증액 상한) | `in_force` (부칙으로 확인) | 2020년 이전에 맺은 임대차에도 현행 기준 적용 |

- 시연 스크립트 `eval\lawwatch_demo.py`:
  1. 과거 버전을 기준선으로 등록 → 감지 → 비교 → 영향 카드 → 수정안 → 승인 → 빠른 점검 → 되돌리기
  2. 위 세 장면을 `select_versions`로 실행해 날짜별로 어떤 버전이 골라지는지 표로 출력
  - 출력은 `out\lawwatch\demo\`에 둔다.
- 연혁에서 카드 basis 조문이 실제로 바뀐 다른 사례가 있으면 추가한다. 없으면 조문 1개를 고친 **"모의"** 파일로 감지 흐름을 보이되, 파일 이름과 화면에 "모의"라고 표시한다.
- 시연이 끝나면 **실제 서비스의 현행 카드와 법령 모음은 원래 상태로 되돌린다.** 버전 파일(`criteria\versions\`)은 남긴다.

## 테스트 (`tests\test_lawwatch.py`)
- 조문 비교(추가·삭제·변경·형식 변경), 영향 카드 찾기
- `select_versions`: 5장 표의 일곱 가지 상황
- 부칙 문장 포함 검사(없는 문장이면 unknown)
- 승인 → 되돌리기 하면 파일 해시가 원래와 같음
- 예정 개정은 시행일 전에 현행으로 바뀌지 않음
- 오프라인 모드
- 버전 파일이 없으면 지금 카드와 같음
